**Looking for custom software?** Start with the [company website](https://www.lxobsidianportal.co.za) and [email](mailto:vilanenathan@gmail.com) to discuss your requirements. Work begins with scope, constraints and delivery expectations — not unsupported promises.

**Reviewing my engineering work?** Use the [engineering evidence register](ENGINEERING_EVIDENCE_REGISTER.md), [evaluation standard](PORTFOLIO_EVALUATION.md) and [repository review roadmap](REPOSITORY_AUDIT_2026.md). They distinguish source-confirmed implementation from declared features and unverified outcomes.

**Evaluating an open-source contribution or derivative?** Review the repository's license, upstream attribution and change history. In particular, [LX Obsidian CLI](https://github.com/lx-obsidian-labs/lx-obsidian-cli) explicitly identifies its T3 Code foundation; this portfolio does not claim sole authorship of upstream work.

## How I approach a project

**Understand the problem → design the workflow → implement incrementally → test the claimed behaviour → document trade-offs → deploy and monitor.**

Each project has its own maturity and verification status. A configured workflow is not evidence of a passing run; a live URL is not proof of production readiness. Planned functionality is not represented as implemented functionality.
